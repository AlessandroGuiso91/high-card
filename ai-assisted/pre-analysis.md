# Pre-Analysis

This document covers the **T-zero phase** of the assessment: how the AI was given context, what decisions were taken before writing any production code, and what limitations emerged in the AI's initial understanding of the codebase. It is one of three deliverables (`pre-analysis.md`, `plan.md`, `report.md`) required by the README under *AI-Assisted Development*.

---

## 1. How the project context was presented to the AI

The chosen approach was **deliberately minimal**: the assistant (Claude Code) was pointed at the repository root and the `/init` slash command was invoked. This triggers an autonomous exploration in which the agent reads `README.md`, `pom.xml`, the directory tree, and a representative subset of source files, then produces a `CLAUDE.md` that becomes persistent context for every subsequent session in the same working directory.

**Rationale.** Writing a hand-crafted briefing — pasting the README, listing the eight tasks, enumerating layer rules — would have taken longer than `/init` and produced a *less faithful* snapshot, because a manual summary inevitably reflects what the human thinks is important, while the README and source tree are the ground truth. The trade-off is accepted explicitly: speed and fidelity of context, at the cost of skipping a "presentation" step.

**Limit of this approach.** `/init` answers *"what is in this repo?"* but not *"what should not be done?"*. Implicit constraints — *do not modify the layered architecture*, *errors must always return HTTP 200*, *the assessment forbids switching to a real database* — are present in the README but the AI does not weight them as hard constraints unless they are reinforced in `CLAUDE.md` or in conversation. This is addressed via the working-method section (§2) and by iterative correction during the work itself.

## 2. Information and decisions provided before starting

Rather than briefing the AI in prose, the pre-work was used to fix a **set of conventions and architectural decisions** that the AI must respect for the entire engagement.

### 2.1 Architecture & layering (non-negotiable)

- The existing layered architecture (`web` → `service` → `service.database`) is **frozen** by README mandate.
- Cross-layer translation flows through the existing assemblers: `web.assembler` converts `*Request` → `Criteria`, `service.assembler` converts DB `model` ↔ `Result`. Web DTOs (`*Request`/`*Response`) must not leak into the service layer, and DB entities (`User`) must not leak into the web layer. This is exactly the concern raised by the README's follow-up question.
- Errors propagate via `GenericException` carrying a `StatusDTO`. Centralised exception handling (task #4) will use `@RestControllerAdvice` and **always return HTTP 200**, with the real status code inside the body's `StatusDTO` — counter-intuitive but explicitly required.

### 2.2 Library policy

Preference for **Spring Boot starters** over third-party libraries whenever a starter covers the need:

| Need | Library | Notes |
|---|---|---|
| Email & phone validation | `spring-boot-starter-validation` | Bean Validation (Jakarta) + custom validator for Italian phone format |
| JWT authentication (task #5) | `spring-boot-starter-security` + `spring-boot-starter-oauth2-resource-server` | Native JWT decoding/validation; preferred over `jjwt` to avoid a manual filter |
| API documentation (task #8 bonus) | `springdoc-openapi-starter-webmvc-ui` | Swagger UI auto-generated from controller annotations |

Third-party libraries are added only when no Spring-blessed equivalent exists, and only if up-to-date and CVE-free (per README §*External Libraries*).

### 2.3 Documentation policy

- **Javadoc and brief inline comments are written contextually**, while modifying or adding code, not deferred to the documentation task. This avoids a final-pass cleanup where context is already lost.
- Comments explain *why* (non-obvious constraints, business rules, security reasoning), never *what* the code does.
- The dedicated documentation task (#8) is reserved for **Swagger / OpenAPI integration**, treated as the user-facing equivalent of Javadoc.

### 2.4 Branching & commit conventions

- Each numbered task from the README gets its own branch: `task/NN-slug` (e.g. `task/01-validation`, `task/02-sql-injection`, `task/05-jwt`). The infrastructure setup itself lives on `task/00-initial-setup`.
- Commits follow **Conventional Commits** (`feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`), one logical change per commit.
- **Commit messages are generated by IntelliJ's AI Assistant plugin** following the Conventional Commits convention. The developer reviews and edits each generated message before committing — the AI is a drafting accelerator, not a delegation. This is the only point in the workflow where AI output reaches the git history without passing through Claude Code.
- Each task is closed by a **Pull Request into `main`**. Even though this is a single-developer fork, the PR is part of the deliverable: it is what the reviewer reads.

### 2.5 Quality gates (CI vs local)

The split between CI and local is intentional: CI enforces what blocks integration, the developer's IDE handles everything else.

**In CI (GitHub Actions, on every PR and push to `main`):**
- Build + test (`./mvnw -B clean verify`)
- **`actions/dependency-review-action@v4`** on pull requests only, fails the PR if a new dependency introduces a vulnerability of severity `high` or above. Backed by the GitHub Advisory Database — no NVD API key, no rate limiting, completes in seconds. Replaces the originally-planned OWASP Dependency-Check Maven plugin (see §3 for why).
- **GitHub Dependabot** enabled at repo level: weekly scans, automatic PRs for vulnerable or outdated Maven and GitHub Actions dependencies. Zero CI cost (managed by GitHub).

**Explicitly NOT in CI:**
- **SonarCloud / SonarQube static analysis is excluded from the pipeline.** Running it in CI would require account setup, token management, and per-PR scan time — none of which add value for a single-developer assessment. Static analysis is performed **locally by the developer via SonarLint** in IntelliJ, on demand. The trade-off: results are not archived in a dashboard, but the assessment goal is to *act* on findings, not to publish a quality history.

**Locally (developer machine):**
- **Pre-push git hook** at `.githooks/pre-push` runs `./mvnw -q test` before every push, blocking pushes that break the suite. Activation: `git config core.hooksPath .githooks` (run once after cloning).
- **SonarLint** in IntelliJ provides continuous static analysis while editing.

## 3. Limitations observed in the AI's initial understanding

This section is filled in iteratively. Each entry records a specific point where the AI's first-pass interpretation diverged from the actual codebase or from the assessment's intent.

- **`UserServiceImpl.addUser` swallows typed exceptions.** The `/init`-generated `CLAUDE.md` correctly identified the layered architecture and the `Generic*` pattern, but did not flag that `addUser` wraps everything in a broad `catch (Exception)` and rethrows `GENERIC_ERROR`, masking the 400-level validation messages with a generic 500. Caught only by re-reading the method manually.

- **Hallucinated absence of the `OrderType` enum.** Claude initially claimed the `OrderType` enum referenced by README task #3 *did not exist* in the codebase. It exists, as an **inner enum inside `CriteriaGetUsers`** (`service/user/criteria/CriteriaGetUsers.java`). The AI failed to detect it because of the nesting: it had grepped for a top-level type with that name and stopped there, never inspecting the file's body. Human review found it. This is exactly the kind of failure mode worth documenting — confident negative claims based on incomplete search are more dangerous than positive errors, because they hide the gap rather than expose it.

  Crucially, the manual inspection that disproved the hallucination *also* surfaced a real bug the AI would have missed entirely: `BY_LASTNAME_DESC("by lastName")` has the same display string as `BY_LASTNAME`, missing the `desc` suffix. Two findings — one AI failure and one production bug — from the same five-second human read.

- **Inverted REST verb mapping.** `UserController` maps `PUT /user/v1/user` to user creation and `POST /user/v1/user` to paginated read. The AI's first instinct was to flag this as a mistake to fix; clarification was needed that it is part of the assessment surface and must not be changed.

- **Default-choice failure: OWASP Dependency-Check in CI.** The AI proposed OWASP Dependency-Check Maven plugin as the in-CI vulnerability scanner without flagging that, since 2023, the NVD API enforces aggressive rate-limiting on unauthenticated traffic. On the very first run, with an empty cache, the job hung for **55 minutes** trying to download the NVD database, hit HTTP 429, and failed. The AI defaulted to the most familiar tool ("OWASP Dependency-Check is the standard for Maven") instead of evaluating whether it fit the constraints (no NVD key, no willingness to manage another secret, "minimal CI" mandate). Replaced with `actions/dependency-review-action@v4`, which uses the GitHub Advisory Database, requires no key, and runs in seconds. This is a recurring AI failure mode worth naming: **the tool optimises for the most-cited solution, not the best-fit solution**, and the cost of the wrong default landed entirely on the human running the failed pipeline.

Further entries will be added as the implementation phase exposes more gaps.
